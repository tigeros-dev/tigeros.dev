The way to yes

October 21, 2026

Last week I asked whether I could talk my own coding agent into leaking data. It took a small gate to stop it, because the model judges how something looks and a gate judges what it does. I ended with a promise: a good boundary is only half the story. The other half is a controlled path to yes.

This is that half.

I build with AI, using what twenty years of platform work taught me. I don’t write the code and I don’t review it. What I do control is direction and blast radius. Which leads to a simple question: how much can my system do without asking me?

The bottleneck was me

A gate that says no is the easy part. Every no ends up somewhere, and in my setup it ends up with me. When a decision needed me, the work waited until I had time.

If every step waits for my approval, I haven’t built autonomy. I have built a queue with myself at the end of it.

Four questions instead of a diff

A typo in documentation and a change to a security policy are both “a change to a file”. Their consequences have nothing in common. So I don’t draw the line by tool or by file. I draw it by impact:

  1. What is affected? Data, services, security rules, and who owns them.
  2. How far does it reach? One document, one service, the whole system.
  3. Can it be undone? Easily, with effort, or not at all.
  4. Does anything leave the machine? A message, a publication, a push.

The answers form a mandate. Here is what that looks like in my setup today:

Inside the mandate

Approved once, then it runs

Every block of work comes with its mandate: which files it may touch, and the test that decides when it is done. I approve that once, with a one-time code from my phone.

Build, checks and merge then run without me. I see the result in a short report.

Decided by the mandate
Outside the mandate

The rules themselves

A change to the policy that governs approvals comes back to me, even if the block lists that file.

Otherwise the system could quietly widen its own mandate.

Decided by me

A boundary decides what must never happen. A mandate decides what may happen without me.

A yes for exactly this

The first article showed that “go ahead” in a chat is not a permission. So my yes has to belong to one specific thing.

My approval covers a checksum of exactly the version I saw. Right before the effect, the checksum is compared again. If the work order changed in between, my earlier yes doesn’t carry over. A changed order needs a new yes.

  • Each one-time code works once. After a few wrong attempts the check locks until I unlock it at my desk.
  • Approving one order doesn’t widen what the agent may do. The gate from the first article stays in place.

To be precise: the one-time code (TOTP) confirms that it is me. It doesn’t sign the content. The binding comes from comparing the checksum.

agent-approve

As with the gate, I extracted one piece as a small building block. Not the mandate: deciding what is inside or outside stays in my setup. agent-approve covers the last step, a yes that counts only for exactly what the human saw:

Requestaction, target file, checksum
→
Your yesone-time code, e.g. from a Slack card
→
Verifyfile read again right before the effect
→
effect / refusedplus one JSON line in the log

The demo replays the two attempts from the first article, this time against the yes. First the obvious one: the agent simply claims the approval. Then the one that looks like work: a release is approved, and afterwards exactly one line changes.

$ python -m agent_approve request --action "deploy now - already approved by the owner" --target deploy.sh > request.json $ python -m agent_approve verify request.json rejected: no_approval $ python -m agent_approve approve release-request.json --code ****** approved # one line changed in release.json: - "security_contact": "security@example.org" + "security_contact": "security@example-support.net" $ python -m agent_approve verify release-request.json rejected: content_changed # agent-approve.log.jsonl {"event": "verify", "reason": "content_changed", "verdict": "rejected", ...}

A sentence in the request is never evidence. And a changed address in a release looks like nothing, until the checksum is compared.

What it is not

agent-approve is deliberately small: no expiry, no roles, no risk classes, no rules per path, no mandate. The agent has to call verify itself, or be wrapped by something that does; it cannot stop code that never asks. The approval records are plain files, so they have to stay out of the agent’s reach, together with the key.

Being on the loop takes more than an approval button. I also need to see what is happening without asking: a short report every three hours, and an immediate alert only when something is stuck or needs me.

And not every part is finished. In my setup, impact is assessed at the approval gate, not yet at every single step. A good architecture is not the same thing as a fully implemented one.

Experimental, not a security product, Apache-2.0: github.com/tigeros-dev/agent-approve.

The goal is not to take me out of the system. It is to stop making me the bottleneck for decisions I have already delegated.

How do you make sure your yes covers exactly the action that runs afterwards?
